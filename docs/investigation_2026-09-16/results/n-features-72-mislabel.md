# Item 25 `n-features-72-mislabel` — result (2026-09-16)

Code/log item. No training was run. Script: `docs/investigation_2026-09-16/scripts/n-features-72-mislabel.py`
(runs in ~30 s; extracts `src/prc` at each submission's commit, builds features on the January 2025 raw file
with that commit's own code, stubs `_fit` so `predict_fold` reveals the exact column lists without fitting).

## 1. Hypothesis (plan.md §1 item 25, source P 7)

"72 features" (handoff §2: 特徴量列数 72、初日から変更なし、うちエンコーディング 9 列) is a frame width that
includes `month`, not the width of the matrix LightGBM saw; the matrix width changed between builds
(80+10 for v1/v2/v8, 97+10 for v3/v4, 98+10 today), and the meaning of `n_features` in
`experiments/experiments.jsonl` changed at 97e67c6.

## 2. Procedure

1. Map each submission to the commit whose code produced it.
   - `experiments/submissions.jsonl` → exp_id per version; `experiments/experiments.jsonl` → `git_sha` per exp_id.
   - v1–v4 records were deleted by 4e807b5 ("drop the v1-v8 history"); recovered with
     `git show 4e807b5 -- experiments/experiments.jsonl` and `git show ea04ec9:experiments/{experiments,pipeline}.jsonl`.
   - `git log --format='%h %ad %s' --date=iso-strict` for commit times vs `uploaded_at`.
2. Read the column-selection code at each commit:
   `git show <sha>:src/prc/{features,train,weather,pipeline,schema}.py`, `git diff <a> <b> -- src/prc/...`,
   plus the config file the submission used (`git show <sha>:configs/...yaml`).
3. Re-derive the matrix by execution (script): for each (submission, sha, config)
   `git archive <sha> src/prc configs` → scratch dir; run a driver with `PYTHONPATH=<scratch>/src POLARS_MAX_THREADS=1`
   that (a) builds `TrainConfig` from the YAML as that commit's `pipeline.main` did, (b) runs
   `build_departure_features` on `data/raw/training_2025-01-01_2025-02-01.parquet` (307,257 rows), (c) if the YAML
   has `use_weather: true`, calls that commit's `weather.join_weather` with `data/ref/metar_hourly.parquet`,
   (d) replaces `train._fit` with a stub that records `(feature_cols, cat_cols)` and returns zeros, then calls
   `predict_fold(frame, frame, cfg)`, (e) evaluates the expression `run_cv` used for `n_features` at that commit
   (`inspect.getsource(run_cv)`).
   Command: `.venv/bin/python docs/investigation_2026-09-16/scripts/n-features-72-mislabel.py --rows 0`.
4. Current cache schema only: `pl.scan_parquet('data/work/feat_train.parquet').collect_schema()` (132 columns) and
   `pl.scan_parquet('data/ref/metar_hourly.parquet').collect_schema()` (12 columns) — no rows read.

### 3.2 Arithmetic of the counts (all from the executed lists)

- Frame numerics at v1/v2/v5/v8 code = 72 = 71 model-visible columns + `month`. `month` is dropped in
  `predict_fold` (`if c not in (LABEL, "month")`) at every commit; `TAXITIME_SEC_mvt` is already excluded by
  `numeric_feature_columns` via `BLANKED_DEP_COLS`. The 9 encoding columns (`ENCODING_COLS`) are joined inside
  `predict_fold` after the frame is built and are therefore **not** part of the 72.
- Model A numeric = 71 + 9 encodings = 80 (v1/v2/v5/v8). Model B numeric = 80 − 15 = 65: `predict_fold` drops
  the columns whose names start with `mvt_minus_aobt3`, `aobt3`, `lobt_minus`, `mvt_minus_lobt`, `mvt_minus_eobt1`,
  `mvt_minus_iobt` — 7 raw clock columns + `aobt3_null` + 7 `_slog` copies.
- Weather adds 18 numeric columns: `hourly_weather_table` has 10 value columns, but `frozen_wx` is `Boolean`,
  which is not in the dtype list of `numeric_feature_columns`, so `frozen_wx` and `frozen_wx_prev1h` sit in the
  frame and are never given to the model; 9 × 2 (current hour + `_prev1h`) = 18.
- v3/v4 on 9f31cef code: `join_weather` did `with_columns(... .alias("hour_utc"))`, overwriting the Int8
  hour-of-day with a Datetime join key, then `drop("hour_utc")` — reproduced: `hour_utc` absent from the frame.
  71 − 1 + 18 = 88 visible + 9 encodings = 97 (A); B = 82.
- v6 on 062a6f0: `CANDIDATE_COLS` (9, incl. `noise_control`) were opt-out via `exclude_features`, and
  `configs/main.yaml` had none → A = 71 + 18 + 9 + 9 = 107, B = 92. Frame numerics 99 = 72 + 18 + 9.
- v7 / today: `include_candidates` opt-in (97e67c6) hides the 9 → A = 98, B = 83. Frame numerics still 99.

   `v4_*.parquet` exist (submissions.jsonl v1–v4 are backfilled from the bucket; docs/README.md line 169:

   d7073bf (09-11 01:55Z) touches only `docs/03_prior_art.md`. On 9f31cef's committed `join_weather`, the real
   parquet (UTC-aware `MVT_TIME_UTC_mvt`) against the naive METAR hourly table raises
   `SchemaError: datatypes of join keys don't match` (reproduced by the script; also stated in commit 34808da:
   "could not run at all"). Yet v3/v4 were uploaded with weather-on configs. So the working tree, the raw files'
   dtype at the time, or the polars version differed from what is committed; the row for v3/v4 above uses a
   driver-side workaround (cast departures to naive) and reflects the committed column logic only.
2. **Polars/LightGBM versions at v1–v4 time** — no `uv.lock` (handoff §9); dtype-based selection could differ if
   an older polars read the parquet differently. Not recoverable from the repository.
3. **v1's config**: the CV record's git_sha e0099d7 predates 9f31cef; `configs/v1_baseline.yaml` differs between the
   two only in comments and the `note:` string, so the matrix is the same either way.
