# 特徴量ログ

1 実験 1 特徴量。**仮説 / 変更 / 結果 / 判定**だけ書く。

**判定規則**（docs/README §6）: `make compare` の **上位 200 行除外後の 95% CI がゼロを除外**したら採用。
CV full は参考値。**未マッチ行だけを動かす変更は測定不能なので対象外。**

**測定条件**: `folds: [forward]` ＋ `--skip-predict`（約 5 分）。気象あり、model B 127 葉、シード 1。

**ルール**: 10 回連続で改善しなければ終了 / 5 連敗で外部調査して方針転換 / 5 回ごとに振り返り。

## 候補の作り方

候補列は常に計算しておき、`exclude_features` でモデルに見せる列だけを切り替える。
特徴量コードを変えるとキャッシュ再構築に約 4 分かかるため、1 本ずつ測るならこちらが速い。

## 3 連敗時点の分析（2026-09-15）

**3 本とも「わずかに悪化」で、悪化幅が +0.39〜+0.50 とほぼ揃っている。**
仮説の当たり外れなら、悪化幅がここまで揃うのは不自然。

列の中身は正常（欠損ほぼ 0、値も分散）だが、**正解との相関が +0.045 / −0.035 と極めて弱い**。

疑い: **`feature_fraction: 0.8` は各分岐で列をランダム抽出するため、列を 1 本足すと
全部の木で抽出パターンが変わる。**つまり「特徴量の効果」ではなく「モデルの引き直し」を
測っている可能性がある。

→ **`noise_control`（信号を持ちえないハッシュ値の列）を足して検証した。結果: 欠陥だった。**

| 足した列 | 200行除外後 |
|---|---|
| `queue_ahead` | +0.49 |
| `bank_position` | +0.39 |
| `stand_rwy_share` | +0.50 |
| **`noise_control`（信号ゼロ）** | **+0.53** |

**全部同じ。**測っていたのは特徴量の効果ではなく「列を 1 本足すこと自体のコスト」だった。

### 正しい基準（列数を揃えたノイズ列）で測り直した結果

| 特徴量 | 200行除外後（vs ノイズ） | 判定 |
|---|---|---|
| `queue_ahead` | −0.16 [−0.40, +0.08] | 有意差なし |
| `bank_position` | −0.19 [−0.41, +0.07] | 有意差なし |
| `stand_rwy_share` | −0.10 [−0.38, +0.14] | 有意差なし |

害はない。価値もない。**3 連敗（理由は「悪化」ではなく「測定限界以下」）。**

### 測定器の修正

**列を 1 本足すだけでモデルが ±0.5 秒揺れる。**単一特徴量の効果はたいていそれ以下なので、
この設定では検出できない。原因は `feature_fraction: 0.8`（各分岐で列の 8 割をランダム抽出）で、
列数が変わると全部の木で抽出が変わる。

→ **スクリーニングは `feature_fraction: 1.0`（列抽出なし）で行う。**効果を検証中。

## 6 連敗の振り返りと方針転換（2026-09-15）

### 調査（文献）

taxi-out 予測で重要とされるのは **出発行列長・滑走路構成・出発ゲート・重量クラス・taxi 経路の複雑さ**
（Scientific Reports 2026、NASA NTRS 20180002162、arXiv 2111.09139）。
**前 4 つは既に持っている**（混雑 20 列、滑走路、スタンド 1,899 値のカテゴリ、`WK_TBL_CAT`）。

### 測定: そもそも余地があるのか

「条件を完璧に知っていても残る誤差」を群内 RMSE で測った（マッチ行・通常域 206 万行）。

| グループ化 | 群数 | 群内 RMSE |
|---|---|---|
| 空港 | 10 | 368.2 |
| 空港 × 滑走路 | 61 | 354.6 |
| 空港 × スタンド × 滑走路 | 9,117 | 307.5 |
| 空港 × スタンド × 滑走路 × 時間帯 | 68,348 | 284.9 |
| 空港 × スタンド × 滑走路 × 時間帯 × 機種 | 111,303 | **268.1** |
| **現在のモデル（マッチ行 clean）** | | **約 202** |

**モデルは静的属性の理論上限を大きく超えている。** 静的・文脈の軸は飽和。

### なぜか — モデルが解いている問題を取り違えていた

```
model A の学習対象 = TAXITIME − proxy
                  = (離陸 − BLOCK_TIME) − (離陸 − AOBT_3)
                  = AOBT_3 − BLOCK_TIME    ← 2つの記録システムの時計のズレ
```

**「taxi が何秒かかるか」ではなく「時計がなぜズレるか」を予測している。**
混雑・経路・構成の特徴量は、proxy が圧倒している領域に足していたので効かなかった。

### 時計のズレの調査（学習データ 1 か月、152,271 行）

| | |
|---|---|
| ズレの中央値 / 標準偏差 | −60 秒 / **374 秒** |
| AOBT_3 が分単位に丸められている割合 | **96.6%**（＝実測でなく報告値。量子化ノイズは ±17 秒で小さい） |
| **運航者ごとのズレ** | 中央値 **−301〜+56 秒**、標準偏差 **237〜473 秒** |

**報告の癖は運航者ごとに大きく違う。**

### 新しい方向

運航者も空港も既にカテゴリ特徴量だが、**木は行をまたぐ集計を作れない**。
676 運航者 × 10 空港 = 6,760 組を分岐だけで学ぶのと、集計値を直接渡すのは別物。

→ **実験 7: `AIRCRAFT_OPERATOR × ADEP` ごとの時計ズレのターゲットエンコーディング**
（`op_offset_med` / `op_offset_n`。既存のリーク防止機構に載せ、fold ごとに学習側だけで作る）
