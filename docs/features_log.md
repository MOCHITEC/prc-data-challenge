# 特徴量ログ

1 実験 1 特徴量。**仮説 / 変更 / 結果 / 判定**だけ書く。

**判定規則**（docs/README §6）: `make compare` の **CV full の 95% CI と 上位 200 行除外後の 95% CI が、どちらもゼロを除外し、かつ同じ向き**なら採用。
片方だけでは採用しない。**未マッチ行だけを動かす変更は測定不能なので対象外。**

> **訂正（2026-09-25）。** ここは長らく「上位 200 行除外後の CI のみ」と書かれていたが、
> `prc.compare.verdict` は両方を要求する実装で、判定を出してきたのは一貫してコードの側だった。
> P8-B でこの齟齬が初めて結論を分けた（K=200 単独なら採用 −0.35 [−0.59, −0.12]、両方なら却下）。
> **コード側に揃える。** 理由は実績で、両方を要求する規則が `stand_arrival_gap` を −3.62 s と
> 事前評価し、盤面で −3.21 s を出している（誤差 0.41 s）。緩い側の規則が同じ精度を出した記録はない。
> 片方だけ通る変更は「裾だけ動いた」か「全体だけ動いた」のどちらかで、前者は少数行に賭けており、
> 後者はノイズ床（1 列あたり ±0.5 s）と区別できない。

## 3 連敗時点の分析（2026-09-15）

**3 本とも「わずかに悪化」で、悪化幅が +0.39〜+0.50 とほぼ揃っている。**
仮説の当たり外れなら、悪化幅がここまで揃うのは不自然。

列の中身は正常（欠損ほぼ 0、値も分散）だが、**正解との相関が +0.045 / −0.035 と極めて弱い**。

疑い: **`feature_fraction: 0.8` は各分岐で列をランダム抽出するため、列を 1 本足すと
全部の木で抽出パターンが変わる。**つまり「特徴量の効果」ではなく「モデルの引き直し」を
測っている可能性がある。

→ **`noise_control`（信号を持ちえないハッシュ値の列）を足して検証した。結果: 欠陥だった。**

**全部同じ。**測っていたのは特徴量の効果ではなく「列を 1 本足すこと自体のコスト」だった。

### 測定器の修正

**列を 1 本足すだけでモデルが ±0.5 秒揺れる。**単一特徴量の効果はたいていそれ以下なので、
この設定では検出できない。原因は `feature_fraction: 0.8`（各分岐で列の 8 割をランダム抽出）で、
列数が変わると全部の木で抽出が変わる。

→ **スクリーニングは `feature_fraction: 1.0`（列抽出なし）で行う。**効果を検証中。

## 6 連敗の振り返りと方針転換（2026-09-15）

### 調査（文献）

taxi-out 予測で重要とされるのは **出発行列長・滑走路構成・出発ゲート・重量クラス・taxi 経路の複雑さ**
（Scientific Reports 2026、NASA NTRS 20180002162、arXiv 2111.09139）。
**前 4 つは既に持っている**（混雑 20 列、滑走路、スタンド 1,899 値のカテゴリ、`WK_TBL_CAT`）。

### 測定: そもそも余地があるのか

「条件を完璧に知っていても残る誤差」を群内 RMSE で測った（マッチ行・通常域 206 万行）。

| グループ化 | 群数 | 群内 RMSE |
|---|---|---|
| 空港 | 10 | 368.2 |
| 空港 × 滑走路 | 61 | 354.6 |
| 空港 × スタンド × 滑走路 | 9,117 | 307.5 |
| 空港 × スタンド × 滑走路 × 時間帯 | 68,348 | 284.9 |
| 空港 × スタンド × 滑走路 × 時間帯 × 機種 | 111,303 | **268.1** |
| **現在のモデル（マッチ行 clean）** | | **約 202** |

**モデルは静的属性の理論上限を大きく超えている。** 静的・文脈の軸は飽和。

### なぜか — モデルが解いている問題を取り違えていた

```
model A の学習対象 = TAXITIME − proxy
                  = (離陸 − BLOCK_TIME) − (離陸 − AOBT_3)
                  = AOBT_3 − BLOCK_TIME    ← 2つの記録システムの時計のズレ
```

**「taxi が何秒かかるか」ではなく「時計がなぜズレるか」を予測している。**
混雑・経路・構成の特徴量は、proxy が圧倒している領域に足していたので効かなかった。

### 時計のズレの調査（学習データ 1 か月、152,271 行）

| | |
|---|---|
| ズレの中央値 / 標準偏差 | −60 秒 / **374 秒** |
| AOBT_3 が分単位に丸められている割合 | **96.6%**（＝実測でなく報告値。量子化ノイズは ±17 秒で小さい） |
| **運航者ごとのズレ** | 中央値 **−301〜+56 秒**、標準偏差 **237〜473 秒** |

**報告の癖は運航者ごとに大きく違う。**

### 新しい方向

運航者も空港も既にカテゴリ特徴量だが、**木は行をまたぐ集計を作れない**。
676 運航者 × 10 空港 = 6,760 組を分岐だけで学ぶのと、集計値を直接渡すのは別物。

→ **実験 7: `AIRCRAFT_OPERATOR × ADEP` ごとの時計ズレのターゲットエンコーディング**
（`op_offset_med` / `op_offset_n`。既存のリーク防止機構に載せ、fold ごとに学習側だけで作る）

## 実験 7: 運航者 × 空港の時計ズレエンコーディング（`op_offset_med` / `op_offset_n`）

**仮説**: model A が実際に予測しているのは `AOBT_3 − BLOCK_TIME`（時計のズレ）。
そのズレは運航者ごとに中央値 −301〜+56 秒と大きく違う。運航者も空港もカテゴリ特徴量だが、
**木は行をまたぐ集計を作れない**ので、6,760 組の中央値を直接渡す価値がある。

**結果**（forward fold、ノイズ列基準）

| 除外行数 | 差 | 95% CI |
|---|---|---|
| 0 | −0.17 | [−0.40, **+0.07**] ゼロを跨ぐ |
| 200 | **−0.26** | [−0.52, **−0.01**] ゼロを除外 |
| 2,000 | **−0.24** | [−0.43, **−0.06**] ゼロを除外 |

月単位ブートストラップ −0.17 [−0.18, −0.17]、P=1.000。マッチ行 203.3 → 203.1。

**判定が割れた。** 頑健版（＝検証済みの判別器）は本物と言い、全行版は有意差なしと言う。
全行版の CI が広いのは尾部のせいで、**0.26 秒は原理的に全行版では見えない**（検出限界 0.25 秒）。

規則の 2 条件のうち、**本番との一致が検証されているのは頑健版の方**（§6: 気象は頑健版有意→本番一致、
model B は頑健版非有意→本番が全行版と逆）。全行版の条件は「効果が大きいこと」を要求しているだけで、
正しさの条件ではない。

**ただし結果を見てから規則を変えるのは危険**なので、採用の前に
**独立した fold（1月）で再現するか**を確認する。再現すれば採用、しなければ棄却。

### 実験 7 の最終判定: 棄却

独立 fold（1月）で再現テスト → 点推定は一致（forward −0.26 / 1月 −0.23）だが 1月は行数が半分で CI が
ゼロを跨いだ。2 fold 統合（481,715 行）でも判定レベル（200 行除外）で **−0.17 [−0.40, +0.05]** とゼロを跨ぐ。
**事前宣言どおり棄却。規則は変えない。**

全スライスで改善側に一貫しており「たぶん本物だが約 0.17 秒」。**測定器の分解能 0.25 秒を下回る。**

## 結論: マッチ行の特徴量エンジニアリングは打ち止め

**証拠**

1. **静的・文脈の空間は飽和している。** 空港×スタンド×滑走路×時間帯×機種を完璧に知っていても
   群内 RMSE は 268.1。モデルは **202** で既に大きく超えている。
2. **モデルが解いているのは taxi の物理ではない。** model A の学習対象は `AOBT_3 − BLOCK_TIME`＝
   2 つの記録システムの時計のズレ。混雑・経路・構成は proxy が圧倒する領域。
3. **4 つの異なる系統で全敗**（行列・運用モード・時計ズレ・外部データ・未使用列）。
4. **効きそうなものは全部 0.25 秒未満**で、測定器の分解能を下回る。

**残っている未着手**（記録として）

- `CALLSIGN_flt` / `ADES_FILED_flt` / `ARVT_3_flt`（未使用列）
- `planned_flight_s` は判定レベルで惜しかった（マッチ行 −0.4 秒）。分解能をさらに上げれば採用できる可能性

## 測定方法について学んだこと

**ノイズ列という対照群が無ければ、実験 1〜3 で「3 本とも有害」という誤った結論を出していた。**
`feature_fraction: 0.8` では列を 1 本足すだけで ±0.5 秒モデルが揺れ、それが特徴量の効果を埋めていた。

→ スクリーニングは **`feature_fraction: 1.0`** ＋ **候補 vs ノイズ列**（列数を動かさない）で行う。
